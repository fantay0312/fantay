# Authoring a good design system: the rules

`SKILL.md` has the procedure; these are the rules behind it. A design system exists so later agents can build on the brand. Author it from the brand's real sources (codebase, attached files, decks, guidelines).

- **DESIGN.md is usage rules for a consuming agent.** Imperative sentences that name tokens, styles and assets ("Set body copy in `--text-base`; `--fg` on `--surface`; the accent only for the primary action"). No title block (the host shows the system's name), no provenance, build notes or "next steps": those go in your reply. Its length tracks the source. A files-only drop earns a few bullets; a real codebase or guide earns sections with the brand's own examples:
  - content fundamentals: tone, casing, I or you, emoji or not, with real copy quoted;
  - visual foundations: color, type, spacing, imagery, motion, states, borders, shadows, radii, layout;
  - iconography: which icon system, format, emoji or glyphs.
  Never pad. Use headings that describe the actual system; a heading added only to reach a count is padding.
- **Assets are copied, never approximated.** No logo in the sources: set the name in plain type and note the absence; never draw or reconstruct a real company's mark from memory, and never rebrand with an identity the user did not provide. Copy the brand's own icons (font, sprite, SVGs). If they are truly unreachable, substitute the closest match and flag it under iconography.
- **The source defines the inventory.** Tokens: the source's real names and values, in its order. Components: exactly the families the source defines, with no "usual" extras (toast, avatar, and so on) unless listed under "Intentional additions" with a reason. Only a from-scratch or guidelines-only brand gets a standard set. Enumerate the full inventory first, track against it, build all of it. If you stop, report exactly what remains and ask; never end silently incomplete.
- **Exact values from real sources.** The source beats any library it resembles (shadcn, MUI and so on). Copy paddings, radii, sizes and line-heights exactly: 5px stays 5px, with no snapping to a grid. Code is truth, screenshots are lossy guidance; previews recreate, never reinvent. If reads fail partway, say what you did and did not read, and never invent names, structure or values.
- **One source for every value.** `tokens.css` holds every value. `DESIGN.md`, `system/studio.json`, `components.html` and `preview/` pages reference tokens with `var(--name)` and never restate a literal that a token already holds. When prose names an accent, scale, rhythm or duration, the binding in `tokens.css` expresses the same decision.
- **A usage note on every token and asset**, saying where it is used. A single-ink SVG's note names its ink (an `<img>` cannot inherit color).
- **Legible in every theme.** A text color's usage note names the grounds it reads on ("body copy on `--surface` and `--surface-warm`"), and each such pair holds at least 4.5:1 contrast (WCAG 2; 3:1 for text of 24px and up or bold 19px and up, and for any border, focus ring, icon or other mark that carries meaning) in every theme. Check the later themes' values, not only the first's. What previews and component fixtures paint meets the same floor. Colors you choose (a brand from scratch, a preview's own styling, the focus ring) simply meet it: a dark theme that lightens an accent usually wants dark text on it, so give such a fill an `on-` token (`--accent-on`) rather than literal white, and make a focus ring you choose solid and at least 3:1 on every surface it lands on, stated under visual foundations. A real source's pair that misses stays exact; say so in its note rather than quietly re-tinting the brand.
- **Accessibility asks have fixed meanings.**
  - A high-contrast theme is an added theme, never a re-tint of the brand's own: every text color at least 7:1 on the grounds its note names (4.5:1 for text of 24px and up or bold 19px and up), with surfaces and controls set apart by borders that meet 3:1, not by shade alone.
  - Color-blind-safe status colors: each status carries a word or an icon too, and success and danger are never a green and a red told apart by hue alone. Either they differ in lightness by at least 3:1 between themselves, or success leaves the red-green axis toward blue (an orange danger beside a plain green does not count). A real source's green and red that miss this stay exact; the safe pair goes in an added theme beside the brand's own, and their usage notes say which theme is safe. With no brand hues to keep, start from the Okabe and Ito set, darkened where it is text.
  - A check for either lists the failing pairs per theme, each with a proposed fix, before editing anything.
  - The user's explicit instructions take precedence over these definitions, and a real source's own colors stay exact.
- **Guidelines say what the consumer provides** (props, children, container, data) plus when to use the component and the do and don't.
- **Seed real substance.** Every theme filled where it differs, the type scale wired to the brand's real font files, and for each component a live example plus a usage entry in `system/studio.json` (`usage`, `avoid`, `accessibility`, `api`, `variants`, `states`).
- **Avoid AI tropes** unless the source truly has them: bluish-purple gradients, emoji as decoration, rounded cards with a colored left-border accent, filler stats, overused fonts (Inter, Roboto, and the like). No filler content; a targeted change stays targeted; never recreate a company's proprietary UI for someone who does not work there.
- **Chart colors.** If the system will carry dashboards or charts, define a categorical order, a sequential hue, a diverging pair and status colors as tokens, and validate them with the `dataviz` skill's palette validator for light and dark. Say so under visual foundations.
